## What this is

Abbey — a hybrid persona/role CLI/TUI in Rust with pluggable executor
backends: `ollama` (preferred default, local `gemma4:26b-mlx`) · `grok` ·
on-device `fm` · the sibling `abi` CLI · the `claude` CLI · optional
`cursor-agent`. It mimics compatible surfaces from Grok Build, Codex, and Claude
Code; it does not reimplement their runtimes. No backend is a hard requirement:
local verbs work with none installed, and generation uses whichever executor
resolves. Personas (Abbey/Aviva/Abi) come from the sibling `abi-ai` crate; the
Max/Gemma worker roles are defined locally in `src/roles.rs` and are model-alias
bindings resolved in `src/models.rs` — not bundled weights.

Brand: **Intelligence Without Limits**, with a claims ledger
([docs/brand.md](../docs/brand.md)). IWL is Abbey/ABI only; Quesar keeps Private
AI operations and does not inherit the tagline.

## Orientation

- `src/` — the `abbey` library and the `abbey` CLI; `src/bin/abbeyd.rs` is the
  second binary (the daemon). `src/app_core/` is the presentation-neutral
  contract layer shared by the CLI (`src/commands.rs`), the daemon
  (`src/daemon/`), and the desktop client. The TUI does **not** import it: it
  reaches the shared model resolution through `src/effective_model.rs`.
- `src/train/` — the consent-gated local training orchestration (`consent`,
  `dataset`, `split`, `redaction`, `trainer`, `evaluate`, `ledger`, `runs`).
  These are the retained legacy verbs; native `abbey train family` lives in `crates/abbey-learning/`.
- `desktop/` — the Tauri 2 + React/TypeScript client, a **workspace member**
  (`desktop/codegen`, `desktop/src-tauri`). `desktop/Cargo.toml` and
  `desktop/Cargo.lock` are deleted on purpose; the root `Cargo.lock` is the
  only lockfile.
- `tests/` — process-level CLI suites plus `app_core_contract.rs`, which imports
  Abbey as an external library client.
- `tools/` — the Python gate tools (`check_claims_sync.py`,
  `check_instructions.py`, `check_p3_readonly.py`), the toolchain helpers
  (`cargo.sh`, `toolchain-env.sh`, `toolchain_policy.py`), `gate_lock.sh`, and
  `tools/ci/`.
- `tasks/` — the workflow ledger: `goals.md` (stable goal blocks), `todo.md`
  (checkboxes), `lessons.md` (durable lessons).
- `docs/` — `architecture.md` (layers, module map, docs map), `claims.md`

## Three things that bite

1. **Toolchain**: Rust **1.99.1 stable**, edition 2024, pinned in
   `rust-toolchain.toml`. Use `./tools/cargo.sh ...` (not bare `cargo`) when
   Homebrew Rust shadows rustup on `PATH`; it also refuses Cargo configuration
   that would substitute the qualified compiler.
2. **Sibling repos are mandatory**: `../abi` and `../wdbx` are path dependencies,
   so even a default build fails without them. Keep the three checkouts adjacent
   and adjacent-only — mixing git and path sources of shared crates produces
   non-unifying crate identities. CI pins `ABI_REVISION` / `WDBX_REVISION` /
   `ABI_TOOLCHAIN` in `.github/workflows/rust.yml`; those need not match your
   local siblings — but **Abbey must behave the same against the pinned
   revisions**. That is stronger than compiling against them: a sibling
   revision that answers differently turns a passing local run into a red CI
   run. `tools/ci/verify-pinned-siblings.sh` proves which one you have.
3. **The gate is `./check.sh`, not `cargo test`.** A bare `cargo test` compiles
   none of the three feature-gated modes, so it can pass while a gated surface
   is broken.

## Commands and the gate

- `./check.sh` — the merge bar. Ordered steps: gate lock → toolchain probe →
  `cargo check --quiet --locked` → `cargo fmt --package abbey -- --check` →
  `cargo clippy --locked --all-targets -- -D warnings` → `cargo build --locked
  --bins` + `cargo test --locked` → three feature cohorts → four
  warning-denied private-item rustdoc passes → Python tool tests → claims sync
  → instruction drift → desktop IPC codegen drift → Program 3 boundary →
  installer smoke → file-size guard → soft cross-compile → opt-in coverage
  (`ABBEY_COVERAGE=1`).
  - The **default** cohort covers the whole workspace, client included, because
    `Cargo.toml` lists every member in `default-members`. The three feature
    cohorts are scoped to the packages that own the feature (`-p abbey`, plus
    `-p abbey-desktop` for `personal-edition`, which the client also has),
    because rebuilding the Tauri tree for a cohort that cannot use it costs
    minutes and gigabytes.
  - Every gate cargo call is `--locked` **except** `cargo fmt` (which takes no
    such flag) and the opt-in `cargo llvm-cov --summary-only`, so the gate
    cannot rewrite the tracked `Cargo.lock`.
- One test, one file, one package:
  - `./tools/cargo.sh test --locked --test cli_surface` — that integration file
    only.
  - `./tools/cargo.sh test --locked --test cli_surface print_bypasses_the_route_log_where_ask_appends`
    — one test inside one file.
  - `./tools/cargo.sh test --locked doctor_reports_the_real_state_it_runs_against`
    — by name across the default members.
  - `./tools/cargo.sh test --locked -p abbey --features wdbx` — a feature-gated
    surface. Always name the package: without `-p` the client is built too, and
    it has no `wdbx` or `accel` feature, so that is not worth the Tauri rebuild.
  - `tools/cargo.sh` never adds `--locked` for you, and
    `./tools/cargo.sh --abbey-qualify-toolchain` is a *mode switch*: it
    qualifies the compiler and exits without running a cargo command.
- `python3 tools/check_claims_sync.py [--write]` — verify or regenerate the
  claims ledger and every generated region. It **builds and runs** the `abbey`
  binary under the qualified toolchain to read the manifest, so it takes minutes
  after a source change; `ABBEY_CLAIMS_SYNC_TIMEOUT` (default 900 s) widens the
  budget. `--write` is the only flag — the default mode *is* the check.
- `python3 tools/check_instructions.py` — enforces the AGENTS.md/CLAUDE.md split.
- `python3 tools/check_p3_readonly.py` — Program 3 read-only boundary.
- `cargo run --locked --quiet -p abbey-desktop-codegen -- --check` — desktop
  IPC codegen drift (the root gate step). Regenerate with
  `(cd desktop && bun run codegen)` after changing `src/app_core/` or
  `src/effective_model.rs`.
- `desktop/check.sh` — the client gate. It adds what the root gate cannot run
  (bun typecheck/tests/build, bundle security, a linked binary, a live scratch
  `abbeyd` read) and needs bun plus a WebView host. The three macOS acceptance
  provers are **opt-in** — `ABBEY_DESKTOP_ROUTES_ACCEPTANCE=1`,
  `ABBEY_DESKTOP_PACKAGED_ACCEPTANCE=1`,
  `ABBEY_DESKTOP_MENU_ACCEPTANCE=1` — and need Accessibility permission and a
  packaged bundle.
- `sh tools/ci/cross-compile-guard.sh` — soft Linux/Windows cross-checks.
  Skipped when the targets are not installed (`rust-toolchain.toml` declares no
  `targets`), and never a hard gate.
- `ABBEY_CARGO_FEATURES=personal-edition ./install.sh` — install the separately
  named personal edition. `ABBEY_CARGO_FEATURES=wdbx` builds the in-process
  WDBX backend.
- `tools/ci/verify-pinned-siblings.sh` — run the gate against the sibling
  revisions CI pins. The local `../abi` and `../wdbx` checkouts carry their own
  in-flight work, so a sibling that is mid-change can fail this gate for
  reasons that have nothing to do with Abbey; this helper overrides the
  sibling path dependencies to clean archives of the pinned revisions and
  writes nothing into either checkout.

Full command table: `CLAUDE.md`. For docs-only edits run the scoped checks
above instead of the whole gate.

## Training and learning

`abbey train family` is the native Rust collection, LoRA/Adam, evaluation and
export pipeline described in `docs/model-family.md`. It has no Python runtime
fallback. Exact supported architectures and qualification limits remain explicit;
source text learning and synthetic tensors do not qualify an assistant release.
Its writing/worker paths require the existing training consent-file contract,
plus the separate private-training line when examples are private. Dynamic
repository learning never implicitly opens personal memory databases.

The following rules describe the **retained legacy** `abbey train` verbs. They
own no neural trainer, optimizer, loss, or weights: their implementation is a
curation-to-artifact pipeline that delegates the weight update across a process
boundary to the sibling `abi` binary; `abbey learn` curates the corpus it
trains on. Read the claims rows `training-local-consent-pipeline` (Partial)
and `training-lora-pipeline` (Proposed) before claiming anything about
training quality.

- Verbs: `plan` (read-only preview, writes nothing), `prepare --consent <p>`
  (writes `dataset.jsonl` + `manifest.json`), `run --consent <p>` (train,
  evaluate, decide, record), `evaluate` (re-score the installed artifact,
  writes nothing), `rollback --consent <p> [--to <run-id>]`, `status`.
- **Every writing verb requires `--consent <path>`** — a file holding the exact
  line `abbey-train-consent: v1` on a line of its own (`src/train/consent.rs`).
  There is no environment-variable consent and no `--yes` override.
- `--source memory` seals the corpus from curated memory pairs; `--source specs`
  seals it from Abbey's own claim registry (`src/claims/registry.rs`) and the
  goal ledger (`tasks/goals.md`).
- The split is a **pure function of the record id** —
  `sha256("abbey.train.split.v1" || id)`, first 8 hex chars, 80% train / 20%
  validation — with no RNG, so a record lands in the same split on every host
  forever. Redaction (secrets, then paths) runs before the split.
- The trainer runs with a fixed argv grammar —
  `abi nn train --jsonl <dataset> --field text --out <artifact>` — under a hard
  timeout and a bounded captured output; a non-zero exit, a timeout, or a
  missing artifact fails closed and leaves no artifact behind. The binary
  resolves through the existing `abi` backend path: `ABBEY_ABI_BIN`, then
  `abi_bin` in `config.toml`, then `PATH`. The scorer re-invokes
  `abi nn sample --checkpoint <artifact> --seed <c> --n <n>` and compares the
  samples against the corpus.
- The score is a **training-fidelity** measure: greedy self-reproduction of the
  artifact's own training corpus, probed with seeds drawn from the held-out
  split, plus a fail-closed leak check that refuses to promote when a held-out
  pair's text appears in the training corpus. It is explicitly **not** a
  held-out quality or generalization measure — the delegated trainer exposes no
  loss on unseen text. Only an artifact that beats the recorded baseline is
  installed, and every decision lands in the ledger, which is what makes
  `rollback` possible.
- The ledger is `<state>/train/ledger.jsonl`: append-only, one JSON row per
  step, each row stamped with its own digest — evidence in the same shape as
  the route log.
- The curation gate that decides *what trains* lives in `src/learn.rs`, not in
  `src/train/` — see the "distilled pair is not ready" trap below.

## Execution path

The diagram is in [docs/architecture.md](../docs/architecture.md#execution-path); what
follows is the architecture you cannot infer from filenames.

- **One canonical execution path for a persona/role turn.** CLI, slash commands,
  and the TUI all reach the executor through `actions::run_agent` →
  `session::hybrid_run` → `agent::run_resilient` → `AgentConfig::run_capture`
  or `run_interactive`. Do not add a second way to invoke the agent.
- **The bypass inventory is larger than `src/capture.rs`.** Four callers use
  `src/capture.rs`, and the inventory is exactly
  `crate::capture::{run_print, capture_chat, capture_oneshot}`: `print`
  (`commands.rs`), `commit` (`actions::run_commit`), `voice ask` (`voice.rs`),
  and the `learn distill` teacher calls (`distill.rs`, via `capture_oneshot`,
  which never resolves or resumes a conversation). `src/agent/bounded_capture.rs`
  is a *different* module — a `pub(super)` bounded capture helper, compiled and
  tested on every host (the Unix path uses the supervisor instead) — and is not
  part of this inventory. They skip `hybrid_run`: no
  persona/role wrap, no prefs injection, and **no `route.jsonl` row** (proof:
  `print_bypasses_the_route_log_where_ask_appends` in `tests/cli_surface.rs`).
  Three more paths skip `hybrid_run` *without* going through `capture.rs`:
  `hybrid_loop::run_stage` (`hybrid_loop.rs`), the `External` passthrough for
  any unrecognized word (`commands.rs`), and `abbey init --agent`
  (`doctor.rs`). The last two call `run_resilient` directly, so they write no
  route row at all. `abbey subagents` and `abbey improve` sit outside the path
  too: they drive local peer lanes through `AgentConfig::run_capture`, so they
  get no role→model or prefs injection, and write one route-log row per run or
  stage rather than one per lane.
- **Daemon protocol versions are separate negotiated envelopes** over the same
  owner-only Unix socket: v1 read-only (`Status`/`Claims`/`ReadRoutes`), v2
  bounded runs (`SubmitRun`/`GetRun`/`CancelRun`/`RunEvents`), v3 safe
  tool/memory/model/claim authority, v4 conversation contracts
  (`APP_PROTOCOL_V4 = 4`, `APP_SCHEMA_V4 = 2`). v3 and v4 never downgrade and
  never decode each other's JSON. The single exception is the legacy v1/v2
  envelope, where a **v1-only read-only** command may retry once against an
  older daemon that answers `unsupported_version`; mutating v2 commands are
  never downgraded or replayed.
- **Backend precedence** (`src/agent/backend.rs`): `ABBEY_BACKEND` env > config
  `backend` key > legacy `ABBEY_AGENT` > ollama (only when it resolves *and*
  `ollama list` already contains `gemma4:26b-mlx`) > on-device `fm` (only when
  `fm models` reports the `system` model ready) > `grok` → `abi` → `claude` →
  `cursor` last (`LOCAL_FIRST_FALLBACK`; `abi` sits behind `grok` because its
  default completion is a persona template, not a model). A set-but-unknown
  `ABBEY_BACKEND` value selects ollama and does not fall through to config.
  `doctor` shows an automatic choice as
  `backend: … (from auto; default configuration)`.
- **Two backend orders exist, and they are not interchangeable.**
  `LOCAL_FIRST_FALLBACK` (`src/agent/backend.rs`) is the *auto-selection*
  order: `fm`, `grok`, `abi`, `claude`, `cursor`. The TUI's Ctrl-B
  `cycle_next` order is `ollama`, `grok`, `fm`, `abi`, `claude`, `cursor`.
  Do not read one as the other.
- **Executor resolution is best-effort at startup and mandatory only at spawn**
  (`AgentConfig::exec_path`), so every local verb — claims, memory, os, routes,
  installer probes — works on a machine with no executor installed.
- **Edition separation is compile-time** (`src/edition.rs`): the default build
  is the safe edition; `--features personal-edition` selects a separately named
  binary, config root, state root, credential namespace, daemon socket, and
  audit path. The audit path is a *reserved destination* with no writer, and
  `Edition::unrestricted_runtime_implemented()` is false in every edition.
- **Memory has three openers, not one.** `memory::backend_path` is pure — it
  never creates anything, so read-only callers can test `.exists()` first.
  `open_backend_with_timeout` is the interactive opener (the TUI memory panel
  passes 250 ms and renders `unavailable: …`). `open_backend_exact` *rejects*
  an unknown or unavailable backend so an approved mutation can never land in a
  substituted store. The `wdbx` backend is compile-time gated: a default build
  asked for `wdbx` silently falls back to SQLite and says so in `doctor`.
- **The route log is evidence.** `route.jsonl` is append-only and `sync_all`'d,
  and it is written *before* the executor runs. A write that fails **fails the
  turn** instead of losing the record (proof:
  `an_unwritable_route_log_fails_the_turn_instead_of_losing_the_record`).
- **`desktop/` is a member of the root cargo workspace**, not a second one
  (Tauri 2 + React/TypeScript client of the app core). `cargo build`,
  `cargo test`, and `cargo clippy` at the repository root therefore cover the
  client too — one lockfile, one lint, one test run. The client's build lands
  in the *root* `target/`, not `desktop/target/`, and that cache is very large —
  the Tauri dependency tree is built once and reused across the feature cohorts
  (only the client is relinked when the `abbey` crate's features change).
  Check free space before a full gate run: a full disk fails the build with a
  linker error that reads like a code fault.
- **`tasks/` is the workflow ledger**: `goals.md` (stable goal metadata),
  `todo.md` (checkboxes), `lessons.md`. Only each file's claims-summary region
  is generated; the goal metadata and checkboxes are hand-maintained.
- **`zig/` is retained history**, not a product: abbey-zig, folded in
  2026-09-28 with `git subtree add` (phase tags `zig/p1`..`zig/p3`). Do not
  extend it, do not run `./zig/tools/check.sh` as a product gate, do not delete
  it; `zig/AGENTS.md` describes that port. Nothing in the Rust gate reads
  `zig/`, and `zig/contracts/abbey` no longer has to stay byte-identical to
  `contracts/abbey`.
- **`abbey init` scaffolds `AGENTS.md`** in the current directory and refuses to
  overwrite an existing one without `--force`. It targets *other* projects — do
  not run it here; this file is hand-maintained and gated.
- **Desktop Tauri entrypoints**: `desktop/src-tauri/src/main.rs` builds the
  Tauri app and enumerates the IPC surface in `generate_handler!` (37
  commands; the block must stay comment-free because `verify-bundle.mjs` parses
  it by splitting on commas); commands live in `commands.rs`, IPC types in
  `ipc.rs`/`v3_ipc.rs`, frontend in `desktop/src/`, and codegen in
  `desktop/codegen`. The root gate runs only codegen `--check`; the full client
  gate is `desktop/check.sh`.
- **The desktop client picks one of two routes and never blends them**
  (`desktop/src-tauri/src/backend/`). With a bearer configured, every read goes
  over the authenticated socket and a failure is *reported* — never retried
  in-process. With **no** bearer configured, only the v1 reads (status, claims,
  routes) come from the in-process app core; v3 (memory, models,
  claims-by-id) and v4 (conversations) are daemon-only and refuse in-process
  (`backend/v3.rs`, `backend/conversations.rs`). The in-process route also
  rejects `GetRun`/`RunEvents`, so the Runs view is daemon-only.
- **Read-only MCP/daemon boundaries**: `abbey mcp serve` (stdio default,
  `abbey mcp serve http` loopback-only) serves a read-only tool registry —
  no shell, no filesystem mutation, no process spawn; Abbey is not an MCP
  client/host of other providers' servers. The daemon keeps v1 read-only
  (Status/Claims/routes), v2 bounded runs (no tool/shell dispatch), v3 safe
  tool/memory/model/claim authority, and v4 conversations with no execution
  authority. Windows named pipes are unsupported, and the daemon fails closed
  rather than falling back to an in-process core.

## Invariants — do not relax

- **OS execution** (`os_control.rs`) never runs without `--confirm` and only
  against the allowlist, in both editions, with no shell bypass.
- **`Cargo.toml` denies `unsafe_code`** as a manifest lint. Clippy
  `-D warnings` alone would not catch it: every `unsafe` needs an explicit
  `#[allow(unsafe_code)]` with a SAFETY comment.
- **Keep the claims honest.** Current vs. Partial vs. Proposed vs. Blocked vs.
  Out of scope is tracked in `src/claims/registry.rs`; the generated table above
  and `docs/claims.md` follow from it. A capability behind an off-by-default
  feature is "Current behind `--features X`" — and only if the gate compiles and
  tests it. Max/Gemma are role→model bindings, not bundled weights; `/cost` is
  intentionally N/A; alternate CLI wiring is surface parity, not a
  vendor-runtime reimplementation.
- **A feature-gated module is invisible to the default gate.** Adding a
  `[features]` entry without adding the matching clippy/test lines to `check.sh`
  lets the code rot while CI stays green.
- **File size is enforced by `check.sh` for `src/**/*.rs` only**: `main.rs`
  hard-fails over 200 lines; other `.rs` files warn over 800 and hard-fail over
  1000. The desktop client's sources are *not* measured. Split modules before
  the ceiling, not after.
- **`WdbxMemory` holds its `fs4` advisory lock for the handle's whole life**
  (Unix `flock` / Windows `LockFileEx`): acquire `<dir>/abbey.lock` before
  recovery, drop the store before releasing it. The sibling `DurableStore`
  separately holds `<base>.writer.lock`. Preserve both layers. The lock does
  not extend to an `abi` you invoke directly against the same store.
- **Conversation identity is canonical-first.** Commit the opaque canonical save
  or clear tombstone to `runtime.sqlite` first, then recover only the exactly
  marked creation/removal plan through the owner-only fs4-locked journal.
  Identity clear must never delete history, transcripts, memory, models,
  route/run data, or finalized backups. Provider-facing reads use the fallible
  canonical selector; only presentation may use the lossy mirror wrapper.
- **`abbey daemon` and `abbeyd` use the same owner-only Unix socket and exactly
  one bearer source**: `ABBEYD_SOCKET_PATH`, and `ABBEYD_BEARER_TOKEN` xor
  `ABBEYD_BEARER_TOKEN_FILE` (owner-only). Client failures never fall back to
  in-process claims.
- **Self-learn's `train_candidate` path requires provenance**; no silent
  deletes in the reflect/digest flow.
- **State is runtime data.** `~/.local/state/abbey` (including `memory.sqlite`)
  is never committed and does not exist in a fresh checkout.
- **Learned embeddings are opt-in.** Keys come from `ABBEY_EMBEDDING_API_KEY` /
  `OPENAI_API_KEY` (not `config.toml`); changing provider or model creates a new
  isolated vector space and never silently falls back.
- **Diff and git hygiene**: keep changes small and reviewable in the existing
  style; only commit when asked; never force-push `main`; never commit secrets.

## Traps

- **Never branch per-call behaviour on `AgentBackend::from_env()`.** It is
  resolved once per process in a `OnceLock`, while the TUI's Ctrl-B switch
  changes `AgentConfig::backend` at runtime — thread the live `cfg.backend`
  through (`state.read_chat_for(cfg.backend)`,
  `AgentBackend::transcript_subdir()`). Reading the cached value is what let a
  cursor-launched session keep adopting `CURSOR_AGENT_CHAT_ID` after switching
  to `abi`, silently killing continuity: a guard that consults the wrong backend
  is not a guard. The same caching makes `from_env()` order-dependent inside a
  test binary: set `ABBEY_BACKEND` before anything else resolves a backend.
- **Each backend owns its argv grammar** (`src/agent/argv.rs`). `fm`, `abi`,
  `claude`, and `ollama` share none of cursor-agent's flags; their builders
  start from scratch, and tests assert that no foreign flag leaks. Under
  `fm`/`abi`, `hybrid_run` must not inject role→model ids (`fm` vocabulary is
  `system|pcc`; under `abi` a cursor `claude-*` id would read as an explicit
  live request). Under `ollama`, role aliases collapse to `gemma4:26b-mlx`.
  Claude maps Abbey aliases into its own vocabulary and owns its transcript.
- **Ollama never auto-pulls.** Before `ollama run <tag>` is spawned, the tag
  must already appear in `ollama list`; otherwise the turn fails with a
  no-auto-pull error (proof: `tests/ollama_no_pull.rs`). The streamed path
  applies the same preflight.
- **`abi wdbx` takes base paths** (parent dir + base name) while Abbey opens a
  directory — Abbey's `<state>/wdbx/` is `<state>/wdbx/wdbx` to `abi`.
  `wdbx_bridge` translates; passing the bare directory silently reads one level
  up and reports an empty store.
- **Read-only callers use `memory::backend_path`** (pure) instead of opening the
  store; interactive callers use `open_backend_with_timeout` (the TUI memory
  panel uses 250 ms and renders `unavailable: …`). `learn status` once created
  the very store it was meant to report on. Approved mutations use
  `open_backend_exact`, which refuses a substituted backend.
- **A distilled pair is not "ready", and that is the curation gate.**
  `abbey learn distill` writes its teacher answers at confidence **0.6**
  (`src/distill.rs`), while `abbey learn review` counts a pair `ready` only at
  provenance plus confidence ≥ 0.9 (`src/learn.rs`). So a distilled pair shows
  `ready=no` until a human promotes it — that is the intended curation step,
  not a bug, and no verb currently raises an existing pair's confidence
  (`abbey learn train` writes a *new* 0.95 record instead).
- **A low `abbey train` score is often the trainer, not the pipeline.** The
  delegated `abi` trainer is demo-grade and has a **two-character context
  window**, so over real prose it predicts spaces and reproduces nothing — a
  corpus-reproduction score of `0.0000` on prose is the *expected* result, not
  a pipeline fault. Raising the bar needs a delegated trainer with a longer
  context, not a change to `src/train/`. The score is fidelity to the
  training corpus, never held-out quality.
- **The default `install.sh` build has no `wdbx` feature**, so an installed
  `abbey` asked for wdbx falls back to SQLite and says so in `doctor`. Installers
  take the binary and daemon names from `abbey edition --name` /
  `--daemon-name`, so the two editions cannot clobber each other.
  `install.ps1`'s naming is proven by a parser test only — no Windows host has
  run it, so that claim stays Partial.
- **Never run `cargo fmt --all` here.** `--all` also formats the local *path
  dependencies*, so it reaches the sibling `../abi` and `../wdbx` checkouts: a
  sibling's formatting could fail Abbey's gate, and a plain `cargo fmt` run
  would rewrite the sibling's sources. Because they are path dependencies,
  `cargo fmt --all` **rewrites `../abi` and `../wdbx` sources in place** — it
  does not merely read them. Use `cargo fmt --package abbey`; the siblings
  have their own gates.
- **Schema migrations are numbered `.sql` files**, not generated code: they sit
  beside `src/runtime/migrations.rs` (`migration_1_*.sql` … `migration_10_*.sql`),
  each embedded with `include_str!`. A new migration is a new `.sql` file plus
  its constant, an entry in `MIGRATIONS`, and a `CURRENT_SCHEMA_VERSION` bump
  — never inline SQL.
- **Only edit prose outside the generated claims regions.** The regions in
  `AGENTS.md`, `CLAUDE.md`, `README.md`, `docs/*.md`, and `tasks/*.md` are
  rewritten by `tools/check_claims_sync.py --write`; a hand-edit makes the gate
  fail. Change `src/claims/registry.rs` instead.
- **CLAUDE.md is a pointer, not a second rule set.** It may contain only the
  generated claims summary, the pointer paragraph, one `bash` command block, the
  module-map table, and the git-policy block. `tools/check_instructions.py`
  fails on any other heading or prose in CLAUDE.md, on a CLAUDE.md module map
  or command table naming a path that no longer exists, and on any
  editor-side instruction surface (`.cursorrules`, `.cursor/rules`, …) that is
  not a ≤ 8-line pointer to `AGENTS.md`. Those path and pointer checks cover
  CLAUDE.md and the editor-side surfaces only: **this file's own prose is not
  path-checked**, so a path named here can rot silently. The only
  AGENTS.md-specific check is that its git-policy block stays byte-identical
  to CLAUDE.md's.
- **Two source files look live and are not.**
  `src/app_core/v4_types.rs` is **orphaned and never compiled**: it is not
  declared in `src/app_core/mod.rs` and nothing references it, so edits there
  are invisible to the gate — and it imports helpers (`MAX_V4_ITEMS`,
  `MAX_V4_LABEL`, `MAX_V4_TEXT`, `validate_id`, `validate_text`,
  `validate_conversation_id`) that do not exist in `src/app_core/v4.rs`, so
  wiring it in is real work, not a one-line declaration.
  `src/automation_schedule.rs` *is* compiled (declared at `src/lib.rs`) but has
  no caller outside its own tests: it is substrate for a future automations
  surface, not a live feature. Do not build on either without wiring a
  consumer first.
- **The effective model has two authorities, and the answer must name one.**
  The CLI and the TUI resolve it from the live local configuration
  (`effective_model_line`); the desktop resolves it from the route the
  connected runtime published (`EffectiveModel::resolve_for_route`). Both are
  legitimate and they answer the same model for the same pair, so
  `EffectiveModel::source` (`local-config` or `runtime-route`) exists to keep
  them distinguishable. Two traps follow: a report of "the model a turn would
  use right now" must resolve the *selected* route, not the runtime's first
  available one (the Chat surface submits turns on the selected route, so the
  first-available route answers a different question); and a read-only surface
  must not borrow a session that negotiates write authority — the effective
  model opens its own read-only session requesting exactly `ReadRoutes`. The
  discriminator stays in the typed contract, not in the shared doctor line:
  the CLI and the TUI always resolve locally, so their line is unchanged.
- **A claim is not evidence.** The `desktop-tauri-react` row says the Doctor
  reports the effective model a turn would use; that sentence was false while
  the code resolved the first available route. The registry records what the
  code does, so a row that describes intended behaviour is a false claim until
  the implementation matches it.
- **A run budget is only a bound where it is consulted.** The pinned ABI
  revision's `RunContext::finish` reports `StopReason::Completed` without
  consulting the elapsed duration; the duration ceiling is checked only at
  *event* checkpoints. A cold Metal compile that happens before the daemon's
  first event therefore escapes the one-second run budget entirely, and the
  *client's* read deadline is the real bound. A fix must not depend on an
  uncommitted sibling change: CI pins a revision, so a proof that only holds
  against the sibling's working tree is not reproducible. The local `../abi`
  checkout has already moved past the pinned revision and now consults the
  elapsed deadline — wiring Abbey to that local change would break CI.
- **An observer must use the same rule as the behaviour it observes.** The
  conversation recovery path reads `fs::symlink_metadata` and requires a
  regular file; a test observer using `Path::is_file` follows symlinks and
  reports a dangling `pending.json` as absent. The two rules disagree exactly
  on the case that matters.
- **One gate at a time per checkout.** The integration tests spawn the
  binaries the gate builds, from fixed paths inside the shared target
  directory. A second `cargo build` in the same checkout replaces those
  binaries while the first gate's tests are still running, and the tests then
  exercise a *different* build than the one that was compiled — which reads as
  a flaky test and is really a corrupted experiment. `tools/gate_lock.sh`
  takes an exclusive per-checkout lock (`check.sh` and `desktop/check.sh` both
  call it), so a second gate refuses instead of interleaving. The same trap
  applies to a bare `cargo test` run while a gate is in flight.
- **Other sessions share this checkout.** The working tree, the git index, and
  the `target/` directory are shared with every other session working in this
  repo. A `git status` that grows between two commands, a compile error in a
  file you did not touch, or a suddenly flaky integration test is an
  environment race until proven otherwise — read it that way before changing
  code. `tools/gate_lock.sh` serializes `./check.sh` and `desktop/check.sh`
  only; it does not stop another session from editing files or running
  `cargo build`.
- **This checkout carries a second copy of the repo inside it.**
  `.claude/worktrees/mystifying-hopper-3cf11b` is a live git worktree with a
  *stale* `AGENTS.md` and other sources, and `.claude/` is git-ignored, so
  `git status` hides it. A recursive grep from the repo root double-hits every
  file, and a `git worktree list` shows three checkouts. Exclude `.claude/` and
  `zig/` from repo-wide searches, and do not read that worktree's guidance.
- **The working tree is dirty on purpose.** It carries in-flight work (a
  workspace unification, desktop packaging, ledger updates) plus untracked
  verification receipts. `git status` is not a defect list, and HEAD does not
  describe the code you are editing. The `docs/verification/2026-10-20-rust-1991.md`
  receipt also qualifies the compiler against an *older* ABI pin than the one
  `.github/workflows/rust.yml` pins today.
- **Authored CI is not executed CI.** `.github/workflows/rust.yml` defines
  guarded self-hosted `gate (macOS ARM64 adjunct)` and `gate (Linux ARM64)`
  jobs. Each requires its exact runner-availability variable and trusted
  same-repository head. The Linux job was restored 2026-10-22; no Linux
  execution is claimed. The runner inventory at baseline listed one offline
  macOS ARM64 runner, no Linux or Windows runner. Windows native CI remains
  open. A green local gate or skipped job is not CI evidence.
  `ABBEY_LINUX_ARM64_RUNNER` is a repository *variable*, not a variable any
  local script reads.
- **CI checks out the pinned siblings, not your local ones.** A sibling
  revision that answers differently turns a passing local run into a red CI
  run; `tools/ci/verify-pinned-siblings.sh` proves which revision you have
  without writing into either sibling checkout.

## Tests

`tests/` holds process-level CLI suites plus `app_core_contract.rs`, which
imports Abbey as an external library client. Process tests drive
`CARGO_BIN_EXE_abbey` (the daemon suites also need `CARGO_BIN_EXE_abbeyd`, the
second binary from `src/bin/abbeyd.rs`) because some guarantees only exist once
the process runs — real exit codes, real stdout/stderr, and the SIGPIPE reset
before `main`. The gate builds `--bins` before testing so a previous feature
cohort cannot leave a stale executable behind. `daemon_cli.rs` starts real
`abbeyd`/`abbey` processes against owner-only scratch state and must never use
a user's socket or bearer. State-mutating cases must use a throwaway
edition-scoped state directory — use `abbey::edition::ACTIVE.state_dir_env()`
so the safe edition gets `ABBEY_STATE_DIR` and the personal edition gets
`ABBEY_PERSONAL_STATE_DIR`; never hardcode one. `slash_parse.rs` is read-only
but **not hermetic** — it sets no scratch home or state root, so it observes
your real config and any `ABBEY_BACKEND` you have set. The app-core contract
test stays presentation-neutral and must not gain crate-private access.
